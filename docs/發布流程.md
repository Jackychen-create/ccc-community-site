# 發布流程

跟 Aligned 一樣的規則：每個版本都要有研究員看得懂的更新公告，發布前跑測試和檢查。

## 規則

1. **每個版本一則公告**，寫在 `public/changelog.json` 最上面：版本號、日期、白話條目（研究員看得到的改動才寫）。每個版本分開一則，不要把新版本的內容併進舊的那則。
2. 版本號：新功能升第二位（1.7 → 1.8），小修升第三位（1.7.0 → 1.7.1）。網站用 `changelog.json` 第一則當目前版本，研究員那邊會自動偵測到新版本並提示重新整理。
3. 一次上線好幾個版本時，老研究員登入後會一次看到這幾則，所以每則都要寫清楚。
4. 只改後台、研究員看不到的改動，也要寫一則（條目寫「後台：……」），方便之後查。
5. 改了資料庫：把新的 SQL 接在 `supabase/schema.sql` 最後面（標上版本），並在 Supabase 的 SQL Editor 先執行，再部署程式。
6. 改了規則（資格、課程解鎖等）：一起改 `docs/功能說明.md` 和 `PRODUCT.md`。

## 步驟

1. 改完功能 → 在 `changelog.json` 最上面加一則。
2. `npm test`，全部通過（開 PR 時 GitHub 也會自動跑一次，PR 頁面要是綠勾）。
3. `npm run check`，打開 `docs_tmp/RELEASE_NOTES_PENDING.md` 對照這次要上線的公告有沒有漏。
4. 推到 GitHub 的 `main`，Cloudflare 會自動部署（大約 1 分鐘）。要先試的話推到別的分支，Cloudflare 會給一個預覽網址。
5. 打開網站確認新版本正常（上方會出現「網站有新版本」→ 重新整理）。
6. 確認上線後，把 `released.json` 的 `version` 改成這次的版本，一起推上去。

## 檢查會擋下來的情況

- 某一則沒有版本號、日期格式不對、沒有寫改了什麼
- 版本號重複
- `released.json` 的版本不在 `changelog.json` 裡

## 使用教學影片

畫面或流程有明顯改變時，重錄教學影片：`bash tools/tutorial/make.sh`（約 15–20 分鐘，會直接更新 `public/tutorial/`）。說明在 `tools/tutorial/README.md`。

## 兩個人一起改的時候

規則寫在 CLAUDE.md「多人協作」：各自開分支、合併前 rebase 到最新 main、版本號撞到就改下一號、一次只發一個版本（`gh pr list` 看有沒有別人在等上線）。
